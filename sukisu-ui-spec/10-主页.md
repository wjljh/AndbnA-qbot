## 2. contentWindowInsets 的准确写法（需求书 §4.1 第 3 问）

**源码原文形态**（1 行引用，仅为结构说明）：

~~~
WindowInsets.systemBars.add(WindowInsets.displayCutout).only(WindowInsetsSides.Horizontal)
—— ui/screen/home/HomeMiuix.kt:114
~~~

拆开看：

| 项 | 值 | 出处 |
|---|---|---|
| 组合方式 | systemBars **加上** displayCutout，再 **only(Horizontal)** 只保留左右 | ui/screen/home/HomeMiuix.kt:114 |
| 这样写之后 innerPadding 的 start/end | = 上述左右 inset（横屏/挖孔机才非 0） | miuix:basic/Scaffold.kt:324-341 |
| innerPadding 的 top | 因为有 topBar，top = 顶栏实测高度（含状态栏 inset），不是 insets.getTop() | miuix:basic/Scaffold.kt:327-332 |
| innerPadding 的 bottom | 主页内层 Scaffold 没有 bottomBar，且纵向 inset 已被 only(Horizontal) 裁掉 → **0dp**；底部留白改由尾部 Spacer 补 | miuix:basic/Scaffold.kt:333-338；ui/screen/home/HomeMiuix.kt:179-184 |
| 库侧默认值（对照） | 若你不写这个参数，默认是 systemBars.union(displayCutout)，纵向也算进来 | miuix:basic/Scaffold.kt:90 |

**为什么只留横向（作者的三个理由，均可从源码验证）**：
1. 纵向顶部已由 TopAppBar 自己吃掉——它无条件加 WindowInsets.systemBars.only(Top)（miuix:basic/TopAppBar.kt:806），若 Scaffold 再算一次纵向，内容会被顶两次。
2. 纵向底部由**外层** MainActivity 的 Scaffold（其 bottomBar = BottomBar）负责，主页不重复算（ui/MainActivity.kt:474-496）。
3. 横向必须保留，否则横屏/挖孔机左右会压到不安全区；库文档也说明 topBar/bottomBar 在场时 Scaffold 只该处理剩余方向（miuix:basic/Scaffold.kt:68-72）。

### 4.4 卡片高度怎么来的（并核实「被 Card 裁切」）

1. **没有显式高度**：外层 Row 只写 height(IntrinsicSize.Min)（ui/screen/home/HomeMiuix.kt:270）——含义「本行高度 = 子项的最小固有高度」。
2. 子项 Card 的最小固有高度 = 卡内三块 Box 固有高度的最大值：
   - 图标块 **110dp**（Icon Modifier.size(110.dp)；offset **不参与测量**，只影响摆放）：ui/screen/home/HomeMiuix.kt:294-298
   - 模式文本块 ≈ 16sp 行高 + 10dp×2 ≈ 39dp【推算】：ui/screen/home/HomeMiuix.kt:312-319
   - 主标题块 ≈ 22sp 行高 + 1dp + 15sp 行高 + 14dp×2 ≈ 73dp【推算】：ui/screen/home/HomeMiuix.kt:325-343
3. 110dp > 73dp > 39dp → **卡高 = 110dp【推算】**。也就是说这个 110dp 大对勾同时充当了「卡高标尺」，不是纯装饰。
   - 【未确证】精确像素未在设备实测。复核：Layout Inspector 量 Card 高度，或截图量 卡高 ÷ (屏宽−24dp)。
4. **裁切属实，机制写清楚**：
   - Card 最终画在 squircleSurface 上：miuix:basic/Card.kt:177
   - squircleSurface = 先画底色 + 内容，再用四角 DstIn 遮罩 carve 圆角，整块包在 CompositingStrategy.Offscreen 图层里：miuix:squircle/SquircleBackground.kt:152-165、:255-278、:281-288
   - Offscreen 图层尺寸 = 节点自身尺寸 → **超出卡片矩形的内容天然被图层边界切掉**，四角再被弧线切一层
   - 所以 110dp 图标往右下推出的 27dp / 31dp 全部看不见，**可见部分 ≈ 83×79dp【推算】**，贴着右下角 → 就是「被 Card 吃掉一角」的观感
   - 若不支持运行时 shader，回退分支是 clip(RoundedCornerShape) + background，**同样会裁**：miuix:squircle/SquircleBackground.kt:161-163

**真实行高怎么算（字体 line-height 是否计入，讲清）**：

- 本页**没有任何一处传 lineHeight**（HomeMiuix.kt 全文无 lineHeight 参数），headline1 / body2 这两个 TextStyle **本身也没定义 lineHeight**（miuix:theme/TextStyles.kt:189-193 只有 fontSize = 17.sp；:165-169 只有 fontSize = 14.sp）。
- 因此每段文本高度 = **字体自身的行高度量**（Compose 在 lineHeight 未指定时按字体的 ascent+descent 排版，不额外加行距）。Roboto/MiSans 的经验比例 ≈ 1.17×字号。
- 公式（可直接套）：

~~~
单行内容高        = H(17sp 标题) + 2dp + H(14sp 值)
行节距(行1→行2)   = 单行内容高 + 24dp
卡片高            = 16dp(上) + Σ各行内容高 + 24dp ×(行数−1) + 16dp(下)
~~~

- 代入 ≈：H(17sp) ≈ 19.9dp、H(14sp) ≈ 16.4dp → **单行 ≈ 38.3dp，行节距 ≈ 62.3dp**；两张卡共 8 行时整块 ≈ 16 + 8×38.3 + 7×24 + 16 ≈ **495dp**。
- 全部标 **【推算】**：不是截图量的，是「无 lineHeight ⇒ 字体度量」推出来的；准确值随设备字体变化，请用 Layout Inspector 复核。
- 另注：因为只取了 fontSize，标题**没有**继承 headline1 其它属性（本版本 headline1 也只有 fontSize，见上引行号）。

**为什么没有分隔线（是设计，不是库行为）**：
1. 库**不会**自动画分隔线——Card / BasicComponent / ArrowPreference 内部都没有 divider（miuix:basic/Card.kt:136-152、miuix:basic/Component.kt:159-258、miuix:preference/ArrowPreference.kt:63-88）。
2. 库确实提供独立的分隔线组件（miuix:basic/Divider.kt），但**主页代码既没 import 也没调用**（ui/screen/home/HomeMiuix.kt 的 import 区 31-92 无 Divider，全文无 Divider 调用）。
3. 分隔感完全由**行自身的 24dp bottom padding** 制造（ui/screen/home/HomeMiuix.kt:485、:490）。
   → 结论：**「没有分隔线」是 SukiSU 的写法选择，库不做任何事**。要分隔线得自己插 HorizontalDivider；SukiSU 只在模块页/KPM 页那样用，主页不用。
